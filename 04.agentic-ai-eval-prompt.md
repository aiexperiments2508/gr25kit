### DIMENSION 1 — Model Layer Design
**What to look for:**
- Is there a model routing strategy, or does one model handle every step?
- Are cheaper/faster models used for low-complexity steps (intent classification, extraction, schema filling, routing, simple summarisation)?
- Are stronger reasoning models reserved only for steps requiring ambiguity resolution or complex synthesis?
- Does every model call return a structured output (JSON schema, Pydantic model, function/tool calling) rather than free-form prose?
- Is there a defined output contract per step?
- Is there a defined failure path if the model returns invalid or malformed output?

### DIMENSION 2 — Tool Design
**What to look for:**
- Do all tools have: clear name, description, input schema, output schema, permission boundaries, timeout behaviour, retry behaviour, and structured error format?
- Are tools designed with strict contracts — no vague natural language strings accepted as input?
- Are read tools separated from write tools?
- Are high-risk write tools (delete, cancel, refund, send, financial transactions) gated behind validation and human approval?
- Are tool outputs machine-readable structured responses, not prose?

### DIMENSION 3 — Memory and State Management
**What to look for:**
- Is workflow state (current step, tools called, tool results, confirmation status) stored separately from long-term memory?
- Is storage chosen by access pattern — low-latency store for conversation/workflow state, application DB for app state, vector DB only for knowledge retrieval, object storage for long-term archive?
- Is there a clear distinction between short-term context (in-prompt) and long-term memory (retrieved selectively)?
- Is context bloat avoided — i.e. is the minimum useful context passed to the model per step?
- Is sensitive data (e.g. full patient records, full customer history) withheld from the model unless specifically required?
- Is a vector database used as a catch-all default (anti-pattern)?

### DIMENSION 4 — Orchestration and Control Flow
**What to look for:**
- Is the control flow explicitly defined, not left to the model to improvise?
- Is there a clear sequence: receive → classify intent → retrieve context → scope check → select tools → validate inputs → execute → inspect results → confirm if needed → generate response → log trace?
- Are simple, known workflows implemented as deterministic pipelines or state machines rather than fully autonomous agent loops?
- Is agentic reasoning reserved for steps that genuinely require dynamic decision-making?
- For complex flows: is graph-based orchestration used (LangGraph, Temporal, LlamaIndex, etc.) with branching, retries, loops, approval gates, and fallback paths?
- For multi-agent systems: is agent-to-agent routing explicitly defined — ownership, handoff format, output contract, conflict resolution?

### DIMENSION 5 — Evaluation (Evals)
**What to look for:**
- Are evals designed in from the start, not bolted on after?
- Is there **trace-level evaluation** — not just final answer quality, but every major step: intent classification, retrieval quality, tool selection, tool arguments, policy compliance, confirmation behaviour, task success?
- Is there a maintained test set covering: happy paths, ambiguous requests, out-of-scope requests, tool failures, malicious inputs, partial information, policy edge cases, escalation scenarios?
- Is this test set used as a regression suite on every model, prompt, retrieval logic, or tool schema change?
- Are sampled async evaluations running in production?
- Are metrics tracked (not just examples): intent accuracy, tool call success rate, invalid schema rate, retrieval hit rate, refusal accuracy, escalation rate, task completion rate, user flag rate, cost per successful task?
- If LLM-as-judge is used, is it combined with deterministic checks and human review for important workflows?

### DIMENSION 7 — Reliability
**What to look for:**
- Are large prompts decomposed into smaller, independently testable steps?
- Are structured outputs validated at every step — with retry on invalid schema and fallback on repeated failure?
- Are all model calls wrapped as unreliable upstream dependencies: timeouts handled, malformed outputs handled, rate limits handled, provider errors handled, degraded quality handled?
- Is deterministic validation separated from model reasoning (e.g. code validates extracted dates, verifies user IDs, checks tool arguments)?
- Does the system behave predictably even when the model does not?

### DIMENSION 8 — Cost and Latency Controls
**What to look for:**
- Is model routing applied to control cost — small models for classification/extraction, large models only where needed?
- Are output tokens limited aggressively — no long explanations where a short answer suffices, no prose where JSON will do?
- Is caching applied to: retrieval results, repeated policy lookups, tool metadata, stable context?
- Are non-blocking tasks (evaluation, summarisation) batched or run asynchronously?
- Is streaming used for user-facing responses that take time?
- Are out-of-scope requests filtered early with cheap intent gates before expensive reasoning steps run?
- Is cost observability in place: tokens in/out per step, cost per conversation, cost per successful task?

### DIMENSION 9 — Observability, Security and Privacy
**What to look for:**

**Observability:**
- Are the following logged per agent run: model name, model version, prompt version, step name, workflow ID, conversation ID, tool name, tool arguments (PII masked), latency, TTFT, tokens in, tokens out, cost, retry count, fallbacks, errors, user feedback, eval scores?
- Can you answer: where exactly did a failure occur — intent classification, retrieval, planning, tool selection, tool execution, policy validation, or final response?

**Security:**
- Is all content reaching the model treated as potentially attacker-controlled?
- Is direct prompt injection from user messages defended against?
- Is indirect prompt injection from retrieved documents defended against?
- Are tool outputs treated as data, not instructions?
- Is raw model output never executed directly (no raw SQL, no shell commands from model-generated text)?
- Are tools given least-privilege permissions?
- Are approval gates in place for risky actions?

**Privacy:**
- Is only the minimum necessary data sent to the model per step?
- Is PII masked at the right layer before reaching the model or logs?
- Are retention policies defined for logs, traces, and conversation archives?
- Are sensitive fields excluded from prompts unless strictly required?
